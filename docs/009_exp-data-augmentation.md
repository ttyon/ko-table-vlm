# 009 실험: 실제 문서 패턴으로 합성 데이터 보강 (3주차)

## 질문
합성 데이터에 실제 공문서의 헤더 패턴·어휘·스타일을 넣으면, 실제 문서 성능이 오르는가? 합성 성능은 유지되는가?

## 판단 근거
- 006: LoRA 후 실제 문서에서 **구조는 개선됐지만 전체 TEDS는 그대로**였다.
- 007: 남은 오류가 **합성 데이터에 없던 것**에 몰려 있었다 — 예산 문서 어휘(`상임위 예비심사`, `확정예산`, `수납`), 3단 헤더, 2줄 헤더.
- 002: 미리보기 비교에서 같은 차이 6가지를 확인.
- → 세 군데의 증거가 같은 원인을 가리키므로, **모델·형식보다 데이터를 먼저 고치는 것**이 기대 효과가 가장 크다고 판단.

## 고려한 대안
| 대안 | 버린/미룬 이유 |
|---|---|
| 모델 키우기 (4B) | 원인이 "본 적 없는 어휘·패턴"이면 크기만으로는 한계 → 011에서 따로 확인 |
| 27B 출력으로 실제 문서 페이지를 가짜 정답 삼아 학습 (증류) | 효과는 클 것으로 보이나 test-real과 같은 PDF에서 페이지를 뽑으면 누수 위험, 다른 문서 수집이 먼저 필요 → 012에서 다음 단계로 제안 |
| 실제 표 일부를 학습에 사용 | 50개뿐이라 평가 세트가 사라짐 |

## 방법
`generate.py --aug --template-p 0.5`, `styles.py` AUG_EXTRA — **특정 셀 값은 복사하지 않고 일반 패턴만** 추가:
1. **헤더 템플릿 3종** (구조의 50%): 연도별 `예산|수납`(또는 `계획|실적`) 반복 / `결산 · 예산(A) · 예산(B) · 증감(B-A, (B-A)/A)` / `국회 심의결과 > 상임위 예비심사·본회의 수정 > 증액·감액·증감` 3단 + 선택적 `감액 사유` 열
2. **2줄 헤더**: `2023\n결산`, `2026\n확정예산` 등
3. **긴 세로 병합**: stub 그룹이 40% 확률로 본문 전체를 덮음 (최대 ~15행)
4. **의미가 일관된 열**: 템플릿에서는 예산 열=금액, 증감=△/+ 숫자, 비율=소수, 증액 열은 `-`가 55%
5. **어휘**: 회계·기금 이름(`일반회계`, `환경개선\n특별회계` …), `기본경비`, `(R&D)`, `(보조)`, `(포상금)`, 감액 사유 문장
6. **스타일**: 진한 청록/파랑 헤더 + 흰 글씨, 점선 행 구분(`dotted_rows`), 좁은 열에서 단어 중간 줄바꿈(`break_all` 40%)
- 데이터: `train_aug` 3,000장 (seed 11, 템플릿 49%, multi_header 77%), 나머지 학습 설정은 006과 동일 (2B, r16, 3,000 iter)
- ood 전용 스타일(주황·진한 남색 헤더, 점선·이중선 테두리)은 보강에 넣지 않음 — ood의 "처음 보는 스타일" 성격 유지

## 학습
97분 (1.9초/iter, 헤더가 길어져 시퀀스 증가), 피크 13.2GB. val loss 최종 0.0156 (006은 0.0050) — val은 **원본 스타일**이라 원본 비중이 절반으로 준 영향.

|---|---|---|---|---|

## 해석
1. **실제 문서에서 의도한 효과가 났다.** 특히 겨냥한 3단 헤더 표에서 +0.108, 병합 배치 오류(span)는 20→9로 절반 이하. 병합 셀 재현율이 27B와 거의 같아졌다 (0.785 vs 0.791).
2. **대신 합성 성능이 떨어졌다** (test −0.013, ood −0.024). 원본 스타일 데이터가 3,000→약 1,500장으로 줄어든 영향으로 추정 → **009b 혼합 실험**으로 확인.
3. **남은 오류는 대부분 띄어쓰기**(text_only 26개, 상위가 `구분`→`구 분`, `증감`→`증 감`). 공백 무시 시 0.932.
   - **내 실수**: 보강 템플릿에 `증 감`, `합 계`처럼 **자간 헤더를 띄어 쓴 정답**을 넣었다. 실제 라벨 규칙(003: 자간 헤더는 붙여 쓴다)과 모순 → 모델이 띄어 쓰도록 배웠다. **합성과 실제의 라벨 규칙을 일치시켜야 한다**는 교훈. 수정안: 렌더링은 CSS `letter-spacing`으로 자간만 벌리고 정답은 붙여 쓰기.
4. 27B와의 격차는 0.064 → **0.039**로 줄었다 (공백 무시 0.070 → 0.039).

## 주의 (평가 세트 오염 위험)
보강 방향은 test-real의 실패를 보고 정했다. 셀 값은 복사하지 않았지만, **같은 기관 문서의 헤더 패턴**에 맞춘 것이라 실제 개선보다 과대평가됐을 수 있다. 다른 기관 문서로 재검증이 필요하다 (012 후속 과제).

- 자간 헤더 라벨 수정은 다음 데이터 버전(v3)에 반영.

## 009b 혼합 실험: 원본 3,000 + 보강 3,000

### 판단 근거
009에서 합성 성능 하락의 원인이 "원본 스타일 데이터가 절반으로 줄어서"라면, 두 데이터를 섞으면 둘 다 얻을 수 있어야 한다.
연산량을 같게 하려고 3,000 iter 유지(각 데이터는 0.5 epoch씩) — "데이터 다양성만 늘렸을 때"의 효과를 보기 위함.

### 결과 (최종 3,000 iter 체크포인트)
| 세트 | 006 원본 | 009 보강 | **009b 혼합** |
|---|---|---|---|
| val 100 | 0.987 | 0.978 | 0.975 |
| test 100 | 0.983 | 0.970 | 0.967 |
| ood 100 | 0.990 | 0.966 | 0.976 |
| **real 50** | 0.898 | 0.923 | **0.798** (잘림 26%) |

학습 91분, 피크 13.1GB, val loss 최종 0.0054 (정상 범위).

### 원인 분석: 반복 생성 붕괴
real 50개 중 **13개가 max_tokens(4,096)까지 같은 단어를 반복**:
```
<td rowspan="2">콘텐츠 시티 시티 시티 시티 시티 시티 …   (합성 어휘 "스마트 시티 조성"의 "시티")
```
긴 텍스트 셀을 읽다가 greedy decoding이 루프에 빠진 것. 합성 val에서는 잘림 0%라 **val로는 보이지 않았다**.

원인을 가르기 위해 반복된 13개만 다시 실행 (진단 실험):
| 설정 | 잘림 | TEDS (13개) |
|---|---|---|
| 혼합, 최종 3,000 iter | 13/13 | 0.400 |
| + repetition_penalty 1.05 | 9/13 | 0.531 |
| **혼합, 2,000 iter 체크포인트** | **0/13** | **0.917** |
| (참고) 009 보강 모델 | — | 0.896 |

### 해석
- **데이터 혼합 자체가 나쁜 게 아니라, 최종 체크포인트가 하필 반복에 취약한 지점**이었다. 2,000 iter 체크포인트는 같은 표들을 보강 모델보다 잘 읽는다.
- repetition_penalty는 표 HTML처럼 `<td>`가 본래 반복되는 출력에서는 근본 해결이 아니다 (9/13 여전히 반복).
- **교훈: "마지막 체크포인트를 그냥 쓴다"는 기본 설정이 위험하다.** 그리고 합성 val만으로는 실제 문서의 반복 붕괴를 잡을 수 없다.

## 009c 체크포인트 선택 규칙

### 판단 근거
009b에서 "마지막 체크포인트"가 실제 문서에서 반복 붕괴했고, 합성 val은 이를 잡지 못했다. README 체크리스트의 "매번 val로 고르고"를 지키면서도 실제 문서 특유의 실패를 걸러낼 기준이 필요했다.
- test-real로 고르면 평가 세트 오염 → 불가.
- **반복·잘림은 정답 없이도 판별 가능**하다 → 같은 PDF에서 검출됐지만 test-real에 넣지 않은 **라벨 없는 실제 표 17개**(`data/real/dev_unlabeled`)의 잘림 비율을 선택 기준에 추가.

### 규칙
체크포인트 1,500/2,000/2,500/3,000 각각: ① 합성 val 앞 100 TEDS ② dev 17개 잘림 수 → **잘림 0인 것 중 val TEDS 최고**.

| 모델 | 1,500 | 2,000 | 2,500 | 3,000 | 선택 |
|---|---|---|---|---|---|
| 혼합 (009b) | **0.988** / 0 | 0.972 / 1 | 0.984 / 0 | 0.975 / **7** | **1,500** |
| 보강 (009) | 0.979 / 0 | 0.978 / 0 | **0.983** / 0 | 0.979 / 1 | **2,500** |

(val TEDS / dev 잘림 수) — 혼합 3,000의 반복 붕괴(7/17)를 dev가 정확히 잡아냈다.

### 선택된 체크포인트 결과
| 세트 | 006 원본 (3000) | 009 보강 (3000) | 009 보강 (**2500**) | 009b 혼합 (**1500**) | 27B zero-shot |
|---|---|---|---|---|---|
| test 100 | **0.983** | 0.970 | 0.967 | 0.980 | (50개: 0.951) |
| ood 100 | 0.990 | 0.966 | 0.982 | **0.991** | (50개: 0.980) |
| **real 50 TEDS** | 0.898 | 0.923 | 0.933 | **0.936** | **0.962** |
| real 공백 무시 | 0.901 | 0.932 | 0.943 | **0.945** | 0.971 |
| real TEDS-S | 0.934 | 0.952 | 0.959 | **0.962** | 0.977 |
| real CER↓ | 0.208 | 0.163 | 0.143 | **0.132** | 0.142 |
| real 병합셀 재현율 | 0.682 | 0.785 | 0.814 | **0.844** | 0.791 |
| real 잘림 | 0 | 0.02 | 0.02 | **0** | 0 |

샘플별 (real): 27B vs 혼합1500 31승 10패 9무 / 혼합1500 vs 원본(006) — 아래 012 종합에서.

## 결론
1. **데이터 보강이 실제 문서 성능을 올렸다**: 0.898 → **0.936** (공백 무시 0.945), 병합 셀 재현율 0.68 → **0.84**, CER 0.21 → **0.13**.
2. **원본과 섞으면 합성 성능도 유지된다** (test 0.980, ood 0.991) — 009의 합성 하락은 "원본 데이터 감소" 때문이었다는 가설과 일치.
3. **CER과 병합 셀 재현율은 27B를 넘었다.** 남은 격차(TEDS 0.026)는 주로 띄어쓰기(내 라벨 규칙 불일치)와 행 수 오류.
4. **방법론 교훈**: 마지막 체크포인트를 그대로 쓰면 위험하고, 합성 val만으로는 부족하다 → "라벨 없는 실제 데이터에서 붕괴 여부"라는 정답 불필요 신호가 유효했다.
5. 이 결과도 같은 기관 문서 패턴에 맞춘 보강이라는 한계(위 "주의")는 그대로다.
