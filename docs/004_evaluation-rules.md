# 004 평가 규칙과 그 변경 이유

## 질문
"맞았다/틀렸다"를 어떻게 정의해야 시스템 간 비교가 공정한가?

## 지표 선택 근거
| 지표 | 정의 | 왜 필요한가 |
|---|---|---|
| **TEDS** | 표 트리(table→tr→td)의 편집거리 기반 유사도, 셀 텍스트 포함 | 표 인식의 표준 지표, 구조+내용 종합 |
| **TEDS-S** | 셀 텍스트를 무시한 TEDS | TEDS − TEDS-S = 글자 때문에 잃은 점수 → "구조 문제인가 OCR 문제인가" 분리 |
| **셀 CER** | 같은 격자 위치 셀끼리 문자 오류율 | 글자 정확도. 단, 행·열이 밀리면 뒤 셀이 다 어긋나므로 구조 오류의 영향도 받음 |
| **병합 셀 재현율** | 정답의 병합 셀 중 위치·span까지 맞힌 비율 | 이 프로젝트의 핵심 난제를 직접 측정 |
| 유효율 / 잘림 비율 | 표를 꺼낼 수 있었나 / max_tokens에 걸렸나 | 생성 모델 특유의 실패(형식 깨짐, 반복) |
| p50/p95 지연, 출력 토큰 | 동시 2요청 조건 | 비용 |

**주의**: 이 TEDS 구현은 thead/tbody를 구분하지 않는다 → 논문의 PubTabNet 수치와 직접 비교하지 않고, **같은 코드로 측정한 시스템끼리만** 비교한다.

## 규칙 변경 이력과 이유

규칙을 바꾸는 것은 결과를 보고 지표를 조작하는 위험이 있으므로, **"이미지만 보고는 맞힐 수 없는 차이"만** 없애고, 바꿀 때마다 **모든 시스템을 다시 채점**했다.

| 버전 | 변경 | 계기(근거) | 효과 |
|---|---|---|---|
| v1 | 태그 `table/tr/td`만, `rowspan/colspan`만, 공백 정리 | 모델마다 `<th>`, `<thead>`, `border` 등 형식이 달라 구조와 무관한 차이 제거 | — |
| **v2** | Unicode **NFKC** 정규화 | Docling 실패 분석에서 셀 오류 상위가 `－`(전각)↔`-`, `…`↔`...` — 눈으로 구분 불가 | Docling TEDS +0.004~0.006 |
| **v3** | 가운뎃점 변형(`・` U+30FB, `ᆞ`, `ㆍ`, `‧`, `∙`) → `·` | PDF 원문은 `・`, 모델은 `·` 출력 — 같은 글자 | 소폭 |
| 민감도 | `--ignore-space` (셀 공백 전부 무시) | 자간 헤더 `구 분` vs `구분`: 모델은 보이는 대로 띄어 씀. 라벨 규칙이 결과를 좌우하는지 확인 | **순위·결론 불변** (보고서에 병기) |

## 공정 비교 원칙
- 느린 시스템(27B, 2B zero-shot)은 test·ood 앞 100개만 실행 → **다른 시스템도 같은 100개로 다시 채점**(`evaluate --limit 100`)해서 비교.
- test-real은 50개 전체를 모든 시스템에 적용.
- n=50/100에서 평균 차이가 작으면 **샘플별 승패(paired)** 를 함께 본다.
