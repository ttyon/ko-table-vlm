# 001 개요와 실험 설계

> 읽는 순서: `001` → `002` → … 번호 순. 각 문서는 **질문 → 판단 근거 → 고려한 대안 → 방법 → 결과 → 해석 → 다음 결정** 순서로 쓴다.
> 개념 설명(TEDS, OTSL 등)은 [`concepts.md`](concepts.md), 주제 선정 과정은 [`topic-candidates.md`](topic-candidates.md).

## 질문
한국어 공문서의 **복잡한 표**(병합 셀, 다단 헤더)를 이미지에서 HTML 구조로 복원할 때,
**소형 VLM(2B)을 합성 데이터로 미세조정하면 기존 파이프라인(Docling)과 큰 VLM보다 나아지는가? 그 비용(속도)은?**

## 왜 이 질문인가 (판단 근거)
- **실제 문제**: 문서 처리 실무에서 가장 자주 깨지는 부분이 표, 그중에서도 병합 셀·다단 헤더다. 한국 예산·통계 문서는 이 구조가 거의 항상 등장한다 (실제로 test-real 50개 중 82%가 병합 셀 포함).
- **라벨 비용**: 표는 HTML로 렌더링하면 정답이 자동으로 생긴다 → 1인 프로젝트에서 수천 장 학습 데이터를 만들 수 있는 몇 안 되는 문서 과제.
- **측정 가능성**: TEDS라는 표준 지표가 있어 구조와 내용을 숫자로 비교할 수 있다.
- **하드웨어**: Mac Studio(64GB)에서 2B 모델 LoRA는 1시간대에 끝난다 → 4주 안에 여러 번 반복 실험 가능.

## 실험 설계에서 내린 결정과 이유

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| **평가 세트를 3개로 분리** (test / ood / real) | 합성 test만 보면 "학습 분포에서만 잘하는" 모델을 좋다고 착각한다. ood는 스타일 일반화, real은 실제 효용을 본다 | test 하나만: 과대평가 위험 |
| **ood = 학습에 없는 폰트·테두리·색** | 모델이 특정 스타일을 외우는지 확인하는 가장 싼 방법 | 다른 생성기: 시간 부족 |
| **real = 실제 공공 문서 + 사람 검수** | 최종 판단 기준. 합성에서의 개선이 실제로 전이되는지가 프로젝트의 핵심 질문 | 공개 영문 데이터(PubTabNet): 한국어 문서 특성 반영 안 됨 |
| **지표 = TEDS + TEDS-S + 셀 CER + 병합 셀 재현율** | TEDS 하나로는 "구조가 틀렸는지 글자가 틀렸는지" 구분이 안 된다. 개선 방향을 정하려면 분해가 필요 | TEDS만 |
| **비교 대상 = Docling, 2B zero-shot, 27B zero-shot** | Docling은 "기존 방식" 대표, zero-shot은 "학습 효과"를 분리하기 위한 기준, 27B는 "모델 크기로 해결되는가"를 보기 위함 | 상용 API: 비용·재현성 문제 |
| **동시 2요청으로 지연 측정 통일** | 서버의 continuous batching을 쓰는 현실적 조건 + 시스템 간 공정 비교 | 단일 요청: 실험 시간 2배 |
| **temperature 0, max_tokens 4096 고정** | 재현성. 반복 생성은 "잘림 비율"로 따로 측정 | 샘플링: 비결정성 증가 |
| **프롬프트 버전 고정** (`prompts.py` v1) | 학습과 추론 프롬프트가 다르면 성능 차이의 원인을 알 수 없음 | — |
