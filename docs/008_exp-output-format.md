# 008 실험: 출력 형식 HTML vs OTSL (3주차)

## 질문
같은 모델·데이터에서 출력 형식만 OTSL로 바꾸면 더 빠르면서 정확도는 유지되는가?

## 판단 근거
- 2B LoRA의 지연은 출력 토큰 수에 비례한다(decode가 병목). HTML은 `<td rowspan="2">` 같은 태그가 셀마다 반복된다.
- OTSL은 격자 칸마다 토큰 하나(`<fcel>`, `<lcel>`, `<ucel>` …)라 짧고, 문법상 항상 직사각형 격자라 형식 오류가 줄 것으로 기대 (Docling/TableFormer 계열이 이 이유로 채택).
- 가설: **출력 토큰 −20% 내외, 정확도 동등**.

## 방법
E2(006)와 데이터·rank·lr·iter 완전히 동일, 정답만 `html_table_to_otsl()`로 변환. 예측은 `otsl_to_table()`로 HTML로 되돌려 같은 지표로 채점.
학습 77분, 피크 13.1GB. val loss 0.0209 → 0.0029 (1000) → … → 0.0023 (3000), 중간 출렁임이 HTML보다 큼.

## 해석
1. 합성에서는 가설대로: 토큰·지연 **−18%**, TEDS −0.005~−0.012.
2. **실제 문서에서는 크게 무너졌다** (TEDS −0.20). 원인을 출력에서 직접 확인:
   ```
   정답:  <td rowspan="2">2023 결산</td> …
   OTSL:  <fcel>2023 … <nl> <ucel><fcel>결산 …   ← 2줄 헤더 셀을 위아래 두 칸으로 쪼갬
   ```
   행이 하나 더 생기고 열이 밀려, 뒤따르는 모든 셀이 어긋난다 (`2023 결산`→`2023`이 상위 오류).
3. 가설적 설명: OTSL은 "격자 칸을 줄 단위로 나열"하는 형식이라 **눈에 보이는 글자 줄 = 격자 행**으로 학습되기 쉽다. 합성 데이터에는 2줄 헤더가 거의 없어서(002) 이 편향이 합성 평가에서 드러나지 않았다. HTML은 셀 단위로 텍스트를 묶어 써서 이 오류에 덜 취약.
4. 반복 생성으로 잘린 출력 4건(8%) → 실제 문서에서 출력 토큰이 오히려 증가.

## 결론과 교훈
- **HTML 유지.** OTSL을 다시 시도한다면 2줄 헤더·셀 내 줄바꿈을 합성 데이터에 충분히 넣은 뒤(009의 보강 데이터로) 재실험.
- **합성 테스트만 봤다면 "OTSL이 더 효율적"이라는 틀린 결론을 냈을 것** — 실제 문서 테스트셋(003)을 만든 이유를 보여주는 사례.
