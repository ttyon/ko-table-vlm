# 003 실제 문서 테스트셋 (test-real) 구축 (1주차)

## 질문
합성 데이터에서 얻은 개선이 **실제 문서에서도** 유효한지 어떻게 확인할 것인가?

## 판단 근거
- 합성 test는 생성기와 같은 분포라 **점수가 과대평가**된다. 실제로 2B zero-shot이 합성에서 0.93~0.96이 나와 "이미 충분히 잘한다"고 착각하기 쉬웠다.
- 프로젝트의 핵심 주장(합성 → 실제 전이)을 검증하려면 실제 문서 평가 세트가 필수.
- 학습에는 **절대 쓰지 않고 평가 전용**으로만 사용 (오염 방지).

## 문서 선정 이유
| 기준 | 선택 | 이유 |
|---|---|---|
| 라이선스 | **공공누리 제1유형**(출처표시) | 평가·공개 결과 발표에 법적 문제가 없도록 이용 조건이 명확한 것만 |
| 표 난이도 | 예산·결산 보고서 | 다단 헤더(3단), 긴 세로 병합, `△` 음수, 2줄 헤더가 집중된 문서 유형 |
| 출처 | 국회예산정책처 「2025 대한민국 재정」(830쪽), 「2026년도 예산안 심의결과」(542쪽) | 게시 페이지에 제1유형 표기 확인, PDF 직접 제공 |

버린 대안: 통계청 보도자료(제1유형 여부를 페이지에서 확인하지 못함), 기재부 첨부파일(본문과 첨부의 라이선스 표기가 다를 수 있음), 스캔 문서(이번 단계에서 라이선스가 명확한 것을 찾지 못함).

## 방법
1. **페이지 샘플링** (`real subset`): 본문에 `(단위`가 있는 페이지 = 표가 있는 페이지(문서별 561/830, 474/542쪽). 그중 문서별 25쪽을 seed 0으로 무작위 추출 → 특정 장(章)에 치우치지 않게.
2. **표 검출·crop** (`real detect`): Docling 레이아웃 모델, 2배 해상도 → 67개
3. **정답 초안**: Docling의 **PDF 텍스트 레이어** 결과 → 글자는 원문 그대로(OCR 오류 없음), 구조만 검수하면 됨
   - 버린 대안: 27B로 초안 → 글자 오류까지 검수해야 하고, 학습 중 GPU를 써야 함
4. **검수**: 이미지와 초안을 한 장씩 대조해 구조를 직접 수정. 1차 31개 → 2026-11-19에 19개 추가 → **50개**
   - 고른 기준: 크기·구조 다양성, 2×3 같은 사소한 표 제외, 큰 표(세로 1,000px 이상, 13~17행)도 포함

## 검수에서 발견한 초안 오류 (Docling PDF 모드)
50개 중 **40개 수정**, 10개는 그대로 정확 (1차 31개 기준으로는 26개 수정·5개 정확).
- 세로 병합 분류 셀(`일반회계`, `특별 회계`, `전력산업 기반기금` 등)이 빈 칸 + 중간 행 텍스트로 쪼개짐
- 다단 헤더(`국회 심의결과 > 상임위 예비심사 / 본회의 수정 > 증액·감액·증감`)의 행 밀림, 빈 칸 채움
- 표 위 `(단위: …)` 캡션이 표의 행으로 들어감
- 여러 줄 셀의 텍스트가 옆 셀과 섞임 (`일반 재화및용역판매수입`, `23,496 등기특별회계 …`)

→ **"Docling 출력을 그대로 정답으로 쓰는 방식"은 불가능하다는 근거**이자, Docling 자체의 약점(병합 셀)에 대한 첫 증거.

## 라벨링 규칙 (그리고 이유)
| 규칙 | 이유 |
|---|---|
| 표 밖 캡션(`(단위: …)`, `주: …`) 제외 | 표 구조의 일부가 아님 |
| 셀 안 줄바꿈 → 공백 하나 | 합성 데이터와 같은 규칙 (학습·평가 일관성) |
| 각주 표시(`1)`)는 PDF 텍스트대로 | 눈에 보이는 내용 |
| 자간 헤더(`구 분`)는 `구분`으로 | 단어 띄어쓰기가 아닌 타이포그래피 — 단, 모델은 보이는 대로 `구 분`을 내는 경향이 있어 공백 무시 채점으로 민감도 확인(004) |
| 가운뎃점 변형(`・`, `ᆞ`)은 채점 시 `·`와 같게 | 004 v3 |

## 한계

- 50개는 작다: 시스템 간 TEDS 차이 0.01 수준은 노이즈일 수 있음 → 샘플별 승패를 함께 보고한다.
